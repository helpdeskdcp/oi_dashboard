# Failure-First Gate — Design

**Status: design/mapping document only. No code changed, no threshold retuned. `failure_gate.py` (4 checks, tested, shadow-gated behind `TI_ENABLE_FAILURE_GATE_SHADOW=false`) exists uncommitted at `.claude/worktrees/build-failure-gate/agents/trading_intelligence/failure_gate.py` — real, working prior art, not yet merged. This document honestly maps what it covers against the user's 8-level specification and what remains unbuilt.**

## The 8-level hierarchy vs. what exists today

| Level | Spec | Exists in repo today? | Covered by `failure_gate.py`? | Gap |
|---|---|---|---|---|
| **0 — Data validity** | Stale/missing/malformed/inconsistent data → NO TRADE | Partial. `generate_signal()` (`oi_engine.py:786,797`) returns `NO_TRADE` when the ATM row is missing or LTP is non-positive. No explicit staleness/timestamp-consistency check exists anywhere in the signal path. | **No.** None of the 4 checks touch data freshness or malformed input. | No check evaluates cycle timestamp age or malformed-row detection independently of `generate_signal()`'s own inline guards. |
| **1 — Hard structural veto** | Resistance/support conflict, invalid/failed breakout, rejection, unsafe SL, blocked target, impossible R:R, severe trend contradiction | Partial, folded into `generate_signal()`'s additive score (`structural_bonus`/`structural_penalty`, `oi_engine.py:861,864`, ±20/-30 depending on ATR-scaled proximity to `nearest_major_level()`) — this is exactly the "can be outweighed" pattern `CONFIDENCE_FACTOR_ISOLATION_REPORT.md` flagged. | **Partially** — `reward_risk` (impossible R:R) and `major_level_proximity` (resistance/support conflict, proximity-to-entry only) are independent PASS/FAIL checks, not additive. | "Invalid/failed breakout," "rejection," and "severe trend contradiction" have no independent veto anywhere — only as `generate_signal()` score adjustments, the exact additive-scoring problem this gate exists to fix. Not yet pulled out as independent checks. |
| **2 — Market structure** | BULLISH / BEARISH / NEUTRAL / TRANSITION | `oi_engine.detect_bias()` produces a bias string for CE/PE routing (not this vocabulary). `regime_profile.classify_market_regime()` produces its own regime states (TRENDING/RANGING/EXPIRY_CHOP/etc.), a different vocabulary again. | **Indirectly**, via the `regime` check, which reuses `classify_market_regime()` wholesale — but its vocabulary isn't the one specified here. | No component produces exactly this 4-state vocabulary; two adjacent-but-different vocabularies exist. Reconciling them is unresolved. |
| **3 — OI/flow** | SUPPORTING / CONTRADICTING / NEUTRAL / UNKNOWN; OI alone must never create a trade | `generate_signal()`'s dual-source agreement check (Angel vs. NSE OI signal) is the closest existing analog, folded additively, active only when `nse_atm_row` is supplied (never in the backtest path per `CONFIDENCE_FACTOR_ISOLATION_REPORT.md`). | **No.** Not one of the 4 checks. | Explicitly deferred in `failure_gate.py`'s own docstring: extracting this cleanly needs `generate_signal()` refactored to expose it as a discrete field first, rather than reimplementing and risking drift. |
| **4 — Participant/crowding/trap** | Explicitly flagged by the user as hypotheses requiring evidence, not to be implemented blind | Confirmed by `ARCHITECTURE_AUDIT.md` §L: nothing in the repository computes this today. | **No.** | Not attempted — correctly out of scope per the user's own framing; would need dedicated evidence-gathering before any check is written. |
| **5 — Probability** | Must mean calibrated P(target before SL), or be honestly labeled "confidence score" — never renamed | The codebase already keeps these as two distinct fields: `Recommendation.confidence` and `Recommendation.probability` (`_calibrated_probability()`), never conflated — see `PROBABILITY_CALIBRATION_AUDIT.md` for how uncalibrated the underlying score actually is. | **No.** `failure_gate.py`'s `confidence` check tests only whether the raw confidence clears the tradeable threshold — it does not gate on calibrated probability at all. | The field-separation discipline already in place is worth preserving exactly as-is, not "fixed." |
| **6 — Expected value** | Mathematically defined, not invented P values | Nothing in the repository computes `P(target)×Reward − P(SL)×Risk` anywhere. | **No.** | See `EXPECTED_VALUE_GATE_DESIGN.md` — correctly cannot be built until Level 5's calibrated probability is real. |
| **7 — Entry** | Only now can BUY CALL / BUY PUT be decided | `generate_signal()` (`oi_engine.py:978-979`) decides this today, unconditionally on levels 0-6 above (before any of them exist as real gates). | N/A — existing decision point, not a check. | Sequencing gap: entry is decided *first* today, then confidence adjustments fold in; the target hierarchy wants entry decided *last*. `failure_gate.py` runs *after* `generate_signal()` already committed (shadow-only, observation-only) — the reverse order, by deliberate choice, since nothing yet has evidence to justify moving it earlier. |

**Honest summary**: `failure_gate.py` gives real, working, independent-veto coverage for part of Level 1 (R:R, level-proximity) and all of Level 5's raw-confidence floor (a threshold check, not a calibration check) — roughly 1.5 of 8 levels, a deliberately narrow first slice, not broader coverage. Levels 0, 3, 4, 6 have zero coverage. Level 2's vocabulary doesn't match what's already computed elsewhere. None of this was hidden — `failure_gate.py`'s own docstring already lists "deliberately not included" items; this table makes the mapping against this specific hierarchy explicit.

## SL/Target Validation

The six questions, checked against `oi_engine.generate_signal()` (`oi_engine.py:745-995`) and `failure_gate.py`:

1. **Is SL structurally meaningful?** Yes, by construction — `sl_price_structural` (`oi_engine.py:960`) projects from the nearest opposing-side OI wall (`invalidation_strike`, selected by minimum distance among correct-side candidates), not an arbitrary percentage. A flat `sl_percent` floor only engages when the structural distance would be wider, per `SL_TARGET_RETUNE_REPORT.md`'s confirmation this floor stayed at its default after a full grid search found no better value.
2. **Is target structurally reachable?** Yes, analogously — `target_price` (`oi_engine.py:938`) projects to the strongest OI wall on the profit side, delta-scaled, with a percent floor as the alternative.
3. **Is target blocked** by an intervening structural level, before reaching the target? **No check exists for this anywhere.** `failure_gate.py`'s `major_level_proximity` checks proximity to entry, not obstruction between entry and target — a materially different, unaddressed question.
4. **Is reward sufficient relative to risk?** Yes — `failure_gate.py`'s `check_reward_risk` (a genuinely new, independent check, `MIN_RISK_REWARD=1.0`, a neutral floor not fitted to this data).
5. **Does market structure support the direction?** Partially — the `regime` check reuses `classify_market_regime()` wholesale, but that function's vocabulary/logic wasn't purpose-built against this exact question; a reasonable proxy, not a tailored answer.
6. **Does the trade remain valid after spread/slippage assumptions?** **No check exists.** Neither `generate_signal()` nor `failure_gate.py` models spread or slippage anywhere in this codebase.

No implementation is proposed here for the confirmed gaps (target-blocked-by-intervening-level, spread/slippage validity, Level 0/3/4/6 coverage) — per the explicit "do not implement yet" instruction for this phase.
